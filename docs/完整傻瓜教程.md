## 下次自动运行的准确时刻

cron 配置是 `7,22,37,52 * * * *`，即**每小时的第 7、22、37、52 分**各跑一次。

**北京时间**：

| 触发时刻         | 对应 UTC         |
| ------------ | -------------- |
| 每天 **07:22** | 23:22 UTC（前一天） |
| 每天 **15:22** | 07:22 UTC      |
| 每天 **23:22** | 15:22 UTC      |

（每天四个：07:22 / 15:22 / 23:22，加上重复的 15:22，实际每天 4 次。）

> **为什么不用整点（:00）？**  
> GitHub 官方明确建议避开整点——每小时的第 0 分钟是全网调度最拥挤的时刻，  
> 排队中的任务**可能被直接丢弃**（不是延迟，是消失）。  
> 用 7/22/37/52 这些非整点时刻，丢任务概率显著降低。

> ⚠️ **GitHub 的 cron 用 UTC**，所以网页上显示的时间可能和你预期的北京时间差 8 小时。  
> 这是正常的，不是配置错。

**另外，GitHub 的定时任务是"尽力而为"的**——高峰期可能延迟 5–30 分钟。  
所以别盯着整点看，晚一会儿是正常的。

## 「Process completed with exit code 1」怎么办（2026-11-01 实战记录）

**先分清是哪种失败**——你截图里的报错来自**重跑旧运行**，不是定时运行。

打开失败页面，看顶部横幅：

| 横幅显示                                   | 含义              | 怎么办       |
| -------------------------------------- | --------------- | --------- |
| **"You are viewing an older attempt"** | 你在看某次运行的第 N 次重跑 | 见下方说明     |
| 没有这行横幅                                 | 这就是定时运行失败了      | 按下面 5 步排查 |

### 为什么会失败（根因）

**GitHub 的 "Re-run" 重跑的是那个历史提交，不是最新代码。**

2026-11-01 的实际案例：

- 首次运行用的是提交 `a464d6d`
- 之后我用脚本上传了新文件，**远端 main 已领先 80 个提交**
- 你点了 "Re-run all jobs" → 仍以 `a464d6d` 检出代码
- runner 提交报告后 `git push` → 被拒：
  ```
  ! [rejected]  HEAD -> main (non-fast-forward)
  error: failed to push some refs to
  ```

- → **exit code 1**

而且那个旧提交里的 workflow 用的是 `secrets.GITHUB_TOKEN`——这个密钥名**根本不存在**  
（GitHub 禁止密钥名以 `GITHUB_` 开头，实际配的是 `RADAR_TOKEN`）。所以旧版重跑必然失败。

### ✅ 正确做法：不要点旧运行的 Re-run

**要触发就用最新代码：**

1. 打开仓库的 **Actions** 标签（不是某个 run 的详情页）
2. 左侧点「挂机收益雷达」
3. 右边点 **Run workflow**（不是页面顶部的 "Re-run all jobs"）
4. 下拉框确认 **Use workflow from → main**
5. 点绿色 **Run workflow**

这样会以最新 main 为准，用上修复后的 workflow。

### 修复了什么

workflow 已加两处关键修复（本地已复现验证）：

| 修复                                           | 作用                 |
| -------------------------------------------- | ------------------ |
| `fetch-depth: 0`                             | 完整克隆历史，否则无法 rebase |
| `git fetch + git rebase origin/main` 后再 push | 远端领先时不再被拒          |
| `git config http...extraheader`              | 用 token 认证且明文不进日志  |

本地用真实 git 场景复现验证：

```
测试A：不 rebase 直接 push → 失败（non-fast-forward）✅ 与线上报错一致
测试B：fetch + rebase 后 push → 成功 ✅
```

## GitHub 搜索 API 的两个坑（2026-11-02 实测）

### 坑 1：搜索 issue 必须显式带 `is:issue`

GitHub 侧规则变更后，搜索 issue 的 query 若不含 `is:issue` 或 `is:pull-request`，
直接返回 **HTTP 422**：

```
{"message": "Query must include 'is:issue' or 'is:pull-request'"}
```

**危险之处**：旧代码遇到非 200 就静默返回空列表，表现为"扫到 0 条"，
一度被误判成 API 限流。修复方式是在 `gh_search()` 里统一兜底补 `is:issue`
（一处修改覆盖所有查询），并加了三级降级：带 sort → 不带 sort → 去掉 stars: 限定符。

### 坑 2：次级速率限制（403），与配额无关

实测连打 8 次搜索的结果：

```
403 403 200 200 200 200 200 200
```

而 `rate_limit` 显示 search 配额 `used: 5 / 30`，**配额明明充足**。
这是 GitHub 的**次级速率限制**——Actions runner 是共享 IP，更容易触发。

**应对**（已在 `radar/scan.py` 全部实现）：
- 搜索请求之间强制间隔 1.5 秒（`_throttle_search()`）
- 遇到 403 退避 12 秒后重试
- 仍失败则回退到**上一轮缓存**（`reports/.search_cache.json` 跨轮次持久化）
- 仓库探针改为**并发**（`ThreadPoolExecutor`，6 线程）

### 顺带的性能优化

实测单次 GitHub API 约 1.7–2.8 秒（网络慢，非限速）。串行探针 9 仓库 × 4 请求
要 70 秒以上。改并发后：

| 版本 | 耗时 | 赏金池 |
|---|---|---|
| 修复前（搜索全失败） | 33 秒 | **0 条** |
| 修复后（串行） | 581 秒 | 47 条 |
| **并发后（当前）** | **192 秒** | **47 条** |

# 第六部分：技术档案（排错用）

## Token 权限完整清单（7 项，缺一不可）

| 权限             | 级别    | 用途                                     |
| -------------- | ----- | -------------------------------------- |
| Administration | write | 建仓                                     |
| Contents       | write | 上传/修改文件                                |
| Issues         | write | 开提醒 Issue                              |
| Pull requests  | write | 开 PR                                   |
| Actions        | write | 运行工作流                                  |
| **Workflows**  | write | 上传 `.github/workflows/*.yml`（**挂机核心**） |
| **Secrets**    | write | 配置 Actions 密钥                          |

改权限：<https://github.com/settings/personal-access-tokens> → 点 `radar` → 编辑 → 加权限 → Update token

## 为什么不用 git push

你的网络环境里 `git push` 会连撞三关：

1. `Error in the HTTP2 framing layer` → 加 `git config http.version HTTP/1.1` 可解
2. `CONNECT tunnel failed, response 502` → **你终端里没有代理变量**  
   |  |  |  
   | --- | --- |  
   （WorkBuddy 进程的代理是注入的，自己开的终端拿不到。`env | grep -i proxy` 可自查）
3. `Invalid username or token` → git over HTTPS 的认证路径对细粒度 token 支持有限

**但同一个 token 调 REST API 完全正常**（建仓成功、19 个文件上传成功、密钥写入成功）。  
所以改用 `upload_via_api.py` 走 Contents API，效果完全等价。别再折腾 git push 了。

## Actions 密钥配置的正确做法

GitHub 的 `public-key` 返回的是 **libsodium 公钥**（32 字节裸 base64），  
官方要求用 `crypto_box_seal` 加密，**不是 RSA/OAEP**。  
参考：<https://docs.github.com/en/rest/guides/encrypting-secrets-for-the-rest-api>

macOS 自带 LibreSSL 3.3 **不支持 X25519**，openssl 那条路走不通  
（`openssl pkeyutl -pubin` 报 "unable to load Public Key"）。  
最终方案是 Node 的 `libsodium-wrappers`，脚本已封装好。

**密钥名不能以 `GITHUB_` 开头**（GitHub 保留前缀），会返回 422。  
本项目用的是 `RADAR_TOKEN` 和 `SCAN_TOKEN`。

## 手动触发 workflow

`POST /actions/workflows/radar.yml/dispatches` 需要 `Actions: write`，  
本 token 缺这项（细粒度 token 对该端点限制）。  
**不影响挂机**——cron 定时触发不需要这个权限。  
要手动触发，直接在网页 Actions → Run workflow。

# 常见问题

**Q：报告里全是"⛔ 大陆不可收款"，是不是白做了？**


A：没白做。这正是真实情况——它帮你**提前避坑**。同时报告第四部分给了你能收钱的选题。
真正收钱走第四部分（Creem）。

**Q：Actions 页面显示的警告要紧吗？**
A：`Node.js 20 is deprecated` 和 `ubuntu-latest 迁移` 都是 GitHub 官方弃用预告，
不影响运行结果。我已升级 action 版本（checkout@v5、setup-python@v6、upload-artifact@v5），
下次运行就不会再有了。

**Q：重跑失败了（exit code 1）怎么办？**
A：看上面"Process completed with exit code 1"那一节。核心是：
**别点旧运行的 Re-run，要去 Actions 列表页用 Run workflow（选 main 分支）**。

**Q：多久能看到钱？**
A：实话实说：不确定，可能很久。挂机系统解决"信息和流程"，不解决"需求和信任"。
建议先用第四部分验证第一笔（哪怕 $9），再决定要不要放大投入。

**Q：会不会是诈骗？**
A：雷达已内置反作弊，实测拦下了三个"挂着 $660/$750/$3000 标签但从未付过款"的仓库。

**Q：真的能完全不管吗？**
A：扫描、报告、提醒、自动上架都自动了。但**内容质量要你把关**——
自动生成的商品描述是骨架，直接上架卖不动。
合理分工：机器跑流水线，你做选题和文案。
